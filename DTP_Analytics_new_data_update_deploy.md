# DTP Analytics — новая схема автоматического обновления данных и деплоя

## Задача

Изменить схему еженедельного обновления данных проекта **DTP Analytics** без изменения продуктовой логики сайта.

- Репозиторий: `cwjechw98-lang/dtp-analytics`
- Прод: `https://dtp-analytics.pages.dev`

## Текущее состояние

Сейчас GitHub Actions раз в неделю выполняет примерно такую цепочку:

```text
download_all.py
↓
build_all.py
↓
git add web/public/data
↓
git commit
↓
git push
```

Из-за этого каждое обновление сгенерированных региональных датасетов сохраняется в истории Git.

## Цель

Перейти на схему, при которой сгенерированные данные больше не коммитятся в Git, а существуют только внутри очередной сборки сайта.

Новая схема:

```text
GitHub Actions по расписанию
↓
checkout исходного кода
↓
установка Python-зависимостей
↓
python download_all.py
↓
python build_all.py
↓
свежие файлы появляются в web/public/data/
↓
npm ci / npm install
↓
npm test
↓
npm run build
↓
web/dist напрямую деплоится в Cloudflare Pages
↓
временная машина GitHub Actions уничтожается
```

## Принципиальные требования

### 1. Никакого отдельного сервера

Всё обновление выполняется на GitHub-hosted runner.

Не требуется VPS, постоянно работающий Python-процесс или отдельная база данных.

### 2. Никаких платных сервисов

Не подключать:

- Cloudflare R2;
- PostgreSQL/PostGIS;
- S3;
- VPS;
- иные сервисы, требующие оплаты, платёжной карты или допускающие автоматические списания.

Используем существующие **GitHub Actions + Cloudflare Pages**.

### 3. Не коммитить сгенерированные данные в `main`

`web/public/data` больше не должен автоматически попадать в новые weekly-коммиты.

История `main` должна содержать:

- исходный код;
- pipeline;
- тесты;
- конфигурацию;
- обычные изменения проекта.

Она не должна продолжать накапливать еженедельные снимки всей базы ДТП.

### 4. Источник данных остаётся прежним

`download_all.py` на каждом плановом запуске получает актуальные данные из существующего источника.

`build_all.py` создаёт тот же набор данных, который ожидает текущий frontend.

### 5. Cloudflare Pages получает уже собранный `web/dist`

После успешного прохождения:

```text
download
→ build_all
→ tests
→ production build
```

GitHub Action должен самостоятельно инициировать production deployment в существующий Cloudflare Pages project:

`dtp-analytics`

### 6. Формат данных сейчас не менять

В рамках этой задачи не выполнять архитектурную миграцию на:

- PMTiles;
- H3;
- MapLibre;
- FlatGeobuf;
- DuckDB;
- PostGIS;
- R2;
- иные новые форматы или хранилища.

Сайт после изменений должен получать те же данные по тем же путям, что и сейчас.

Это отдельная инфраструктурная задача, а не переработка продукта.

### 7. Не ломать обычный deployment кода

Изменения в `main` по-прежнему должны приводить к корректному прод-деплою.

Нужно проверить текущую Git integration Cloudflare Pages и исключить конфликт между:

- автоматическим Cloudflare build после code commit;
- новым прямым deployment из scheduled GitHub Action.

Допустимы два варианта:

#### Вариант A

Оставить Cloudflare Git integration для обычных коммитов кода.

Scheduled workflow отдельно:

```text
скачивает данные
→ собирает проект
→ напрямую публикует web/dist
```

#### Вариант B

Централизовать оба типа deployment через GitHub Actions.

Нужно выбрать более простой и надёжный вариант с учётом текущей конфигурации проекта.

## Секреты и доступы

Если для Cloudflare CLI deployment требуются:

- API Token;
- Account ID;
- Project Name;
- иные credentials,

использовать **GitHub Actions Secrets**.

Требования:

- ничего чувствительного не коммитить в репозиторий;
- переиспользовать уже существующие credentials, если они настроены;
- права Cloudflare-токена сделать минимально необходимыми для Pages deployment.

---

## Поведение при ошибке

Если любой из этапов завершился ошибкой:

- скачивание данных;
- Python pipeline;
- тесты;
- Vite build;

**production deployment не выполнять.**

Текущая рабочая версия сайта должна остаться доступной.

Схема:

```text
download FAILED
        ↓
STOP
        ↓
старый production остаётся

tests FAILED
        ↓
STOP
        ↓
старый production остаётся

build FAILED
        ↓
STOP
        ↓
старый production остаётся
```

## Что изменить в текущем weekly workflow

После успешного перехода удалить логику:

```bash
git add web/public/data
git diff --cached --quiet && echo "NO_CHANGES" || git commit -m "data: еженедельное обновление"
git push
```

Вместо неё добавить:

```text
npm install / npm ci
↓
npm test
↓
npm run build
↓
Cloudflare Pages production deploy
```

---

## Старую Git history не переписывать

В рамках этой задачи:

- не запускать `git filter-repo`;
- не переписывать старые SHA;
- не делать force-push `main`;
- не пытаться удалять старые data-коммиты из истории.

Старые версии данных пока остаются как есть.

Цель текущей задачи — **прекратить дальнейшее накопление**.

Очистку истории, если она вообще понадобится, можно рассматривать отдельно позже.

## Плановый запуск

Сохранить существующий weekly schedule.

Например:

```text
каждый понедельник
↓
GitHub Actions
↓
скачать свежие данные
↓
пересобрать datasets
↓
прогнать тесты
↓
собрать production
↓
задеплоить Cloudflare Pages
```

Также сохранить `workflow_dispatch`, чтобы workflow можно было запускать вручную для проверки.

---

## Проверка после реализации

После изменений вручную запустить workflow через `workflow_dispatch`.

Необходимо подтвердить:

1. `download_all.py` успешно скачал свежие данные;
2. `build_all.py` успешно создал datasets;
3. frontend-тесты прошли;
4. production build Vite успешно собран;
5. новый deployment появился в Cloudflare Pages;
6. `https://dtp-analytics.pages.dev` работает после deployment;
7. сайт получает актуальные данные;
8. после workflow в `main` не появился новый data-коммит;
9. `web/public/data` не добавился в историю Git;
10. следующий scheduled run сможет пройти без ручного вмешательства.

## Что предоставить после выполнения

После реализации дать краткий отчёт:

### Изменённые файлы

Перечислить изменённые workflow/config-файлы.

### Финальная схема deployment

Например:

```text
GitHub main
   │
   ├── code commit ──────────────→ Cloudflare Pages
   │
   └── weekly GitHub Action
          ↓
       download data
          ↓
       build datasets
          ↓
       tests
          ↓
       Vite build
          ↓
       direct Pages deploy
```

### GitHub Secrets

Перечислить названия используемых secrets без раскрытия значений.

### Результат `workflow_dispatch`

Указать:

- статус pipeline;
- статус тестов;
- статус build;
- deployment URL / deployment status.

### Подтверждение

Отдельно подтвердить:

> Еженедельные обновления данных больше не создают коммиты с `web/public/data` в `main`.

## Ограничение задачи

Не использовать эту задачу как повод для дополнительного рефакторинга.

Не менять:

- UI;
- findings engine;
- маршруты;
- продуктовую логику;
- формат текущих JSON;
- визуальный язык;
- архитектуру карт.

Сначала стабилизировать новую схему обновления и убедиться, что она работает.

После этого отдельно будет сформировано следующее ТЗ по развитию DTP Analytics.
