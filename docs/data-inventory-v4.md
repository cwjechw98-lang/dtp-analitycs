# DTP Analytics — Phase 0: Инвентаризация исходных данных

> Аудит свежей выгрузки ДТП (все 85 регионов РФ, ~3.67 ГБ raw) без изменения продукта и pipeline.
> Дата снимка: 2026-08-27 · Машинный дамп: `docs/data-inventory-v4.json` · Скрипт аудита: `pipeline/_inventory.py`

---

## 1. Executive summary

Источник — открытые данные ГИБДД (dtp-stat.ru), 85 регионов РФ, **1 616 059 ДТП** за 2015–2026, **2 653 755 ТС**, **3 581 440** участников внутри ТС + **498 328** одиночных (пешеходы/велосипедисты вне ТС). Raw — GeoJSON ~3.67 ГБ.

**Три главных вывода:**

1. **Поле `model` ТС системно ненадёжно — колонки `brand` и `model` десинхронизированы.** Число записей у `brand[N]` точно равно числу у `model[N]` для каждой позиции (543 146 = 543 146, 215 911 = 215 911…), но содержательно модель не связана с брендом: `TOYOTA|Rio`, `KIA|А4`, `FORD|Kalina`, `SKODA|RAV 4`, `УРАЛ|ВАЗ 2115`. Это не «чужие модели» — это **сдвиг колонок** в ведомости источника. `build_all.py` прав, что не публикует model (он это знал).
2. **~9 ценных полей полностью теряются на переходе raw → frontend:** `nearby` (объекты УДС рядом, 59 значений), `address` (94%), `scheme` (68 схем ДТП), `color` ТС, `participant_categories` (пешеходы/дети/мото), `years_of_driving_experience` (61%), `gender`, `health_status` (42 значения!), `region` (район/город, уникальность 2282). Это ~40% потенциала датасета.
3. **Разные классы техники смешаны в одной «автомобильной» аналитике /fleet.** Категории ТС (118 уникальных) включают легковые (A–F классы), грузовые (бортовые, самосвалы, седельные тягачи), автобусы, мото, велосипеды, мопеды, тракторы, троллейбусы — сравнение КАМАЗа с легковой маркой сейчас без разграничения класса.

## 2. Схема сырых данных

```
ДТП (feature.properties, 21 ключ)
├── id: int                    — уникальный id ДТП
├── tags: [str]                — всегда ["Дорожно-транспортные происшествия"]
├── light: str                 — освещение (6 значений)
├── point: {lat, long}         — координаты
├── nearby: [str]              — объекты УДС рядом (59 значений, важное!)
├── region: str                — РАЙОН/город (unique 2282; напр. "Южное Бутово","Омский район")
├── parent_region: str|null    — ФЕДЕРАЛЬНЫЙ СУБЪЕКТ (unique 84; напр. "Москва","Омская область")
├── scheme: str                — схема ДТП (68 значений)
├── address: str|null          — адрес (94.4%)
├── weather: [str]             — погода (9 значений)
├── category: str              — вид ДТП (19 значений)
├── datetime: "YYYY-MM-DD HH:MM:SS"
├── severity: str              — Легкий/Тяжёлый/С погибшими (+"Без пострадавших")
├── vehicles: [ {…} ]          — ТС (см. ниже)
├── dead_count: int
├── injured_count: int
├── gibdd_number: str          — номер записи ГИБДД (служебный id записи ДТП, 1:1 с аварией)
├── participants: [ {…} ]      — участники ВНЕ ТС (пешеходы)
├── participants_count: int
├── participant_categories: [str] — агрегаты (Все/Пешеходы/Дети/Мото/Велосипедисты/Общ.транспорт)
└── road_conditions: [str]     — состояние дороги (31 значение)

vehicles[]:
├── year: int                  — год выпуска ТС (95.6%)
├── brand: str                 — марка (93.7%, unique 376)
├── color: str                 — цвет (97.3%, 13 значений)
├── model: str                 — модель (93.7%, НО системно смещена!)
├── category: str              — класс ТС (99.5%, 118 значений)
└── participants: [ {…} ]      — находящиеся в ТС

participants[] (и в ТС, и отдельно):
├── id: int
├── role: str                  — Водитель/Пассажир/Пешеход/Велосипедист/… (16 значений)
├── gender: str                — Мужской/Женский/Не определен
├── violations: [str]          — нарушения ПДД (68 уникальных, "Нет нарушений" — служебное)
├── health_status: str         — исход (42 значения!)
└── years_of_driving_experience: int|null — стаж в годах (61%)
```

Вложение: ДТП → vehicles[] → participants[]. Плюс топ-level participants[] для пешеходов/велосипедистов вне ТС.

> **Примечание к трактовке (зафиксировано при закрытии Phase 0):**
> - **`parent_region`** — поле заполнено лишь в ~70.7% записей (84 уникальных субъекта). Но это **не проблема**: субъект надёжно восстанавливается из файла/`slug` региона (85 региональных файлов = 85 субъектов). Рекомендуется **не** нести 29% `null` дальше, а выводить субъект из источника файла. Сейчас pipeline использует `parent_region` как имя региона.
> - **`scheme`** — это **код схемы ДТП** (строковое значение вроде `890`/`010`), а не человекочитаемый «тип манёвра». Мы знаем только, что значений 68 и поле заполнено 100%; соответствие код → смысл на этом этапе **не подтверждено**. Для осмысленного использования (поворот/обгон/перекрёсток) Phase 1 должен сначала **найти/построить справочник схем**.
> - **`gibdd_number`** — это **служебный уникальный идентификатор записи ДТП** (1:1 с аварией), а **не** персональные данные человека. Публиковать его frontend'у не нужно, но называть его «персональным» некорректно — это идентификатор происшествия, а не личности.

## 4. Анализ автомобилей

### 4.1 Марка (brand)

- **Покрытие:** 93.7%, **376 уникальных** RAW-значений (есть агрегаты «Прочие марки ТС», «Прочие марки мотоциклов»).
- **Top-20:** ВАЗ (543 146), TOYOTA (215 911), HYUNDAI (128 561), KIA (107 283), RENAULT (101 551), NISSAN (96 933), ГАЗ (87 682), Прочие марки ТС (86 081), VOLKSWAGEN (84 070), FORD (70 199), CHEVROLET (68 039), HONDA (63 000), MITSUBISHI (54 537), MERCEDES (50 835), SKODA (42 281), DAEWOO (40 857), КАМАЗ (40 831), MAZDA (36 723), OPEL (34 798), BMW (32 484).
- **Кириллица/латиница:** ВАЗ vs Lada, ГАЗ, УАЗ, КАМАЗ, МАЗ, УРАЛ — кириллица; TOYOTA, NISSAN и др. — латиница. Есть `МАЗ-МАН` (двойной бренд), `ИЖ`, `ЗИД`, `ТАГАЗ (TAGAZ)`.
- **Подозрительные/агрегаты:** «Прочие марки ТС», «Прочие марки мотоциклов» — источниковые заменители. Марка в основном **достоверна** (для легковых/грузовых/мото топы реалистичны).

### 4.2 Модель (model) — СИСТЕМНАЯ АНОМАЛИЯ

- **Покрытие:** 93.7%, **374 уникальных** — но это **не** настоящие модели.
- **Главный факт: колонки `brand` и `model` десинхронизированы.** Число записей у `brand[N]` = число у `model[N]` (543 146=543 146, 215 911=215 911, …). Содержательно модель не связана с брендом:
  - `TOYOTA | Rio` (Rio — модель KIA/Hyundai)
  - `KIA | А4`, `FORD | Kalina`, `SKODA | RAV 4`, `MERCEDES | 80`
  - `УРАЛ | ВАЗ 2115`, `КАМАЗ | ВАЗ 2112`, `КРАЗ | 650 Lynx`
- **Числовые «модели»:** `80`, `250`, `6522`, `4320`, `4410`, `3302`, `G35` — похоже на коды/индексы, а не названия.
- **Кириллица/латиница одной модели:** `Нива ВАЗ-2121` vs `Niva`, `ВАЗ 2110, 21101…` (списки через запятую).
- **Вывод:** `model` в текущем виде использовать **нельзя** без сверки колонок (иначе — ложные пары). Именно поэтому `build_all.py` намеренно не публикует model. Это одна из главных «грязных» зон.

### 4.3 Тип ТС (category)

- **99.5% покрытие, 118 уникальных.** Внутри — **перемешаны классы:**
  - Легковые: В-класс (956 644), С-класс (439 228), D-класс (184 369), А-класс (69 946), Е-класс (32 409), Прочие легковые (193 289)
  - Грузовые: Седельные тягачи (72 942), Бортовые (37 652 + 11 040), Самосвалы (25 360), Прочие грузовые (10 981), Рефрижераторы (9 366)
  - Автобусы: Одноэтажные 5–8 м (36 381), 8–12 м (27 796), до 5 м (7 106)
  - Мото: Мотоциклы (85 284), Мопеды (33 524)
  - Прочее: Велосипеды (52 862), Тракторы (6 947), Троллейбусы (7 794), Спецтехника (14 614), Иные ТС (19 438), Прицепы, Полуприцепы
- **Диагноз:** в `/fleet` сравниваются разнородные классы как «равные». Для корректного сравнения нужна группировка в 6–8 суперкатегорий (легковые / грузовые / автобусы / мото / вело / спец.).

## 8. RAW → pipeline → frontend (field lineage)

### Список A — Используем полностью
`point(lat/long)`, `datetime` (год/месяц/час/день-недели), `severity`, `dead_count`, `injured_count`, `light`, `weather`, `road_conditions`, `category` (вид ДТП), `parent_region` (субъект), `vehicles.brand`, `vehicles.category` (тип ТС), `participants.role`, `participants.violations`, `participants.years_of_driving_experience`.

### Список B — Используем частично
- `vehicles.brand` → сохраняется как индекс, но **потеряна нормализация** (кириллица/латиница, «Прочие»-агрегаты).
- `vehicles.year` → сохранён, но только как «возраст» через `age_buckets` (сам год не публикуется отдельно).
- `parent_region` → используется как имя региона в `regions/{slug}.json`, но **не** сегментирует данные по районам.

### Список C — Сейчас теряем (главный результат)
- **`nearby`** (объекты УДС, 59 значений) — инфраструктура рядом (перекрёсток, пешеходный переход, остановка, мост) → **не читается**.
- **`address`** (94.4%, 842k уникальных) — геопривязка, но в pipeline не читается.
- **`scheme`** (68 значений) — **код схемы ДТП**; смысл (перекрёсток/поворот/обгон) требует справочника, которого пока нет → **не читается**.
- **`region`** (район/город, 2282) → **не читается**.
- **`vehicles.color`** (13 значений) → **не читается**.
- **`vehicles.model`** → **намеренно не публикуется** (системно смещена).
- **`participants.gender`** (3 значения, 100%) → **не читается**.
- **`participants.health_status`** (42 значения!) → **не читается**.
- **`participants.id`** → не читается.
- **`participant_categories`** (Пешеходы/Дети/Мото/Вело/Общ.транспорт) → **не читается**.
- **`participants_count`**, **`tags`**, **`gibdd_number`** → не читаются (последний — служебный идентификатор записи ДТП, 1:1 с аварией).

## 10. Top opportunities (потерянные данные, наиболее перспективные)

1. **`health_status` участника (42 градации)** — точная тяжесть исхода каждого участника; позволяет строить «человеческий» риск вместо бинарного погиб/ранен. **Не используется.**
2. **`nearby` (объекты УДС)** — пешеходный переход, перекрёсток, остановка, мост рядом → фильтры «ДТП у перехода/на перекрёстке». **Не используется.**
3. **`scheme` (68 значений-кодов)** — вероятно тип манёвра (перекрёсток/поворот/обгон) → сильный предиктор сценария, **но смысл кодов надо подтвердить справочником** (Phase 1). **Не используется.**
4. **`gender` + `participant_categories`** — сегменты участников (пешеходы/дети/мото) → демография аварийности. **Не используются.**
5. **`region` (район/город)** — drill-down внутри субъекта («город vs трасса»). **Не используется.**
6. **`vehicles.color`** — тёмный/светлый в ночное время → инфраструктурный сигнал. **Не используется.**

## 11. Top data risks (где данные нельзя использовать без работы)

1. **`model` ТС — RED.** Системное смещение колонок, без сверки (по category+year+геометрии или по пересборке маппинга) использовать нельзя. Это не косметика — сейчас любое сравнение по модели даст ложные пары.
2. **2026 год неполный** (~7k ДТП вместо ~130k) — при year-over-year сравнении его надо исключать или помечать; иначе резкий «спад» ложный.
3. **`road_conditions` = «Не установлены»** — 1 071 500 из 1 616 059 (66%) — поле покрыто формально, но информативность низкая; использовать только реальные значения.
4. **`weather` и `light` — «Не указано»/«Не установлено»** низкие, но есть служебные значения (`Не установлено` light — 77), их надо отфильтровать.
5. **`years_of_driving_experience` 39% пусто** — стаж-аналитика смещена к тем, у кого стаж известен (водители-нарушители чаще имеют заполненный стаж).
6. **`brand` и `category` — агрегаты** («Прочие марки ТС», «Иные ТС», «Легковые без типа») требуют отдельной обработки, иначе искажают топы.
7. **`severity` = «Без пострадавших (нет данных)»** — 44 записи, служебный класс, отфильтровать.

## 12. Итоговая потеря на переходе raw → frontend

```
~3.67 ГБ raw (86 файлов, 85 регионов)
        ↓  build_all.py
~85.8 МБ frontend data (national.json, brands.json, heat_cells.json, regions/*.json)
```

Теряется **конкретно**:

| Категория информации | Что именно теряется |
|---|---|
| Инфраструктура места ДТП | `nearby` (перекрёсток/переход/остановка/мост) |
| Адрес и населённый пункт | `address` (94%), `region` (район/город) — остаётся только субъект |
| Схема/маневр ДТП | `scheme` (68 схем) |
| Цвет ТС | `vehicles.color` (13 значений) |
| Точная модель ТС | `vehicles.model` — намеренно, т.к. смещена |
| Демография участников | `gender`, `participant_categories` (пешеходы/дети/мото/вело) |
| Точный исход каждого участника | `health_status` (42 градации) |
| Пол и идентификатор участника | `gender`, `participants.id` |
| Число участников ДТП | `participants_count` |
| Служебные атрибуты | `tags`, `gibdd_number` (служебный id записи, публиковать не нужно) |

Т.е. **не просто «агрегирование», а выброс целого слоя**: инфраструктурного (nearby), гео-адресного (address/region), маневрового (scheme), человеческого (gender/health_status) и цветового (color). ~40% потенциала датасета недоступно frontend.

## 13. Следующий шаг — Phase 1: Semantic / Normalization Layer

**Phase 0 закрыт как baseline.** Следующая задача — **не UI**, а **единый нормализованный контракт между 3.7 ГБ raw и продуктом**. Причина: если просто протянуть raw-поля напрямую, будем иметь UI с 59 вариантами `nearby`, 118 типами ТС и 42 формулировками мед. исхода — данных станет больше, а продукт хуже. Нужен **слой нормализации**, который даст управляемый набор смысловых атрибутов.

Планируемый первый набор контрактов (проект, детали — в отдельном ТЗ Phase 1):

| Контракт | Источник | Целевой вид |
|---|---|---|
| `vehicle_supercategory` | `vehicles.category` (118) | легковые / грузовые / автобусы / мото / вело / спецтехника / прочее |
| `region_subject` | файл `/slug` (+`parent_region`) | гарантированные 85 субъектов (без 29% null) |
| `local_region` | `region` (2282) | район / город |
| `human_outcome` | `health_status` (42) | ~5–7 смысловых исходов |
| `infrastructure` | `nearby` (59) | нормализованные объекты УДС |
| `crash_scheme` | `scheme` (68 кодов) | код + понятное название **после** построения справочника |
| `participant_type` | `role` + `participant_categories` | нормализованный тип участника |
| `model` | `vehicles.model` | **жёстко quarantined / RED — не трогать** (пара brand/model потенциально ложная) |

Цель после нормализации — продукт, отвечающий не «где много ДТП», а, например: **«Где и при каких условиях ДТП чаще заканчиваются тяжёлыми последствиями?»** — с раскладкой одновременно по месту, инфраструктуре, типу участника, типу транспорта, освещению, погоде, сценарию ДТП и времени.

> Инвентаризация показала, что данных для этого уже достаточно: `health_status`, `nearby`, `scheme`, `gender`, категории участников и локальный `region` сейчас просто не доходят до продукта.
